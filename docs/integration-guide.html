Commission SDK Integration

Hand it an AIR file, get back what the ticket is worth and whether that figure can be written into a field. One function, plain JSON, no I/O, no dependencies — so the same code runs in a Supabase Edge Function, a queue worker, or a browser.

§1 — Shape

How it fits into a CRM

The SDK computes and explains. It never stores anything, never calls out, and never decides what your CRM does with the answer.

  1. An AIR file lands in your feed.Server Pro, a GDS drop, an email attachment — wherever it already arrives.
  2. You call priceAirFile(text, { config }).Synchronous, no network, about a millisecond per document.
  3. The IATA number on the ticket selects the contract.Not a parameter you pass. A mixed feed sorts itself, and a number you hold no contract for is reported rather than priced against the wrong agency's terms.
  4. You write prefill into your commission field.Null whenever the contract did not settle the question — see §5. That check has already happened, so a caller that writes it without thinking is still correct.
  5. The statement arrives; you call checkStatement.What was earned comes from the tickets, what was paid from the statement, and the result says only where they differ.
the whole integration
import { priceAirFile } from "./commission-sdk.js";

const result = priceAirFile(airFileText, { config, subAgentId: "aappel" });

for (const doc of result.documents) {
  if (doc.prefill !== null) {
    // safe to write — the contract settled it
    await db.tickets.update(doc.ticketNumber, { commission: doc.prefill });
  } else {
    // doc.explanation says why, in one line, for a person
    await queue.forReview(doc.ticketNumber, doc.explanation);
  }
}

§2 — The logic

How a fare is priced

Six steps, in this order. Every one of them can stop the calculation, and when one does the result says which and why.

StepWhat happensWhere it comes from
1 Read the document. Ticket number, carrier, issue date, coupons with their booking classes, the fare, and the taxes itemised by code. The AIR record. Taxes come from the KSTB/KFTF breakdown, never the TAX- line — that one aggregates small taxes into XT and a rule naming a tax code cannot see through it.
2 Select the contract by the IATA number the ticket was issued under. The office line. A number with no configured contract is reported, not guessed.
3 Test every condition the contract's clauses declare: carrier, marketing carrier, issue-date window, where travel originates, tour code, fare type, booking class. Highest priority wins; on a tie, the clause declaring more conditions. A remaining tie is AMBIGUOUS and pays nothing.
4 Build the commissionable fare. Base fare, plus YQ only where the contract says so. Government taxes never. The single biggest source of disagreement with a carrier, so the trace records every component and whether it was included.
5 Apply the rate for the booking class — once for the ticket, or once per direction where the contract prices per half round trip. Attachment A, or whatever table is configured. A class not in the table earns nothing: a class the airline did not list is not one it agreed to pay on.
6 Take the consolidator's retention — a point of the fare — and the sub-agent gets the remainder. The spread is computed by subtraction, so share plus retention always equals the commission exactly.

What a reissue and a refund do

A reissue carries the fare of the ticket it replaces plus whatever was collected on top, so commissioning the whole new fare pays a second time on every dollar carried over. The commission already recognised on the original — the Amadeus FO element states it — is reversed. A refund reverses the share of the commission matching the fare actually returned, and the cancellation penalty is fare the carrier keeps, so the commission on it stands.

Never assumed

Where a reissue or a refund does not say what the earlier document earned, the result is INCOMPLETE and prefill is null. Assuming zero is exactly what produces a double payment, and it would look like a perfectly ordinary number.

The arithmetic itself

  • No floating point. Every amount is an integer count of minor units. 0.07 × 8290 is 580.2999999999999 in JavaScript; this returns 580.30.
  • Rounding is stated by the contract, applied once, on the magnitude — so a clawback mirrors the entry it reverses to the cent.
  • Splits sum back to the whole. A fare divided across two sectors, or a commission split between consolidator and sub-agent, is allocated by largest remainder. Nothing is lost between the halves.
  • Currency comes from the document. A EUR ticket is priced in EUR. Amounts in different currencies are never added — a mixed batch totals the majority and says so.

§3 — Deployment

A Supabase Edge Function

The SDK builds to one ESM file with no dependencies, so a Deno function imports it directly. Put commission-sdk.js and your contracts.json beside the function and deploy the folder.

supabase/functions/price-ticket/index.ts
import { priceAirFile } from "./commission-sdk.js";
import contracts from "./contracts.json" with { type: "json" };

const SUB_AGENT = "aappel";

Deno.serve(async (req) => {
  if (req.method !== "POST") {
    return Response.json({ error: "POST an AIR file" }, { status: 405 });
  }

  const airText = await req.text();
  const result = priceAirFile(airText, { config: contracts, subAgentId: SUB_AGENT });

  // The SDK never throws on a bad file; it answers with ok:false and a reason.
  return Response.json(result, { status: result.ok ? 200 : 422 });
});
deploy, then call it
supabase functions deploy price-ticket

curl -X POST "$SUPABASE_URL/functions/v1/price-ticket" \
  -H "Authorization: Bearer $SUPABASE_ANON_KEY" \
  -H "Content-Type: text/plain" \
  --data-binary @26123556000.M07
Why the body is the file

An AIR record is text. Posting it raw rather than wrapped in JSON means no escaping, no size surprises from base64, and --data-binary @file works from any language or a shell script. If your feed already holds the record in a column, post the column.

Pricing a whole batch

One call per file keeps a bad record from affecting the others, and an Edge Function is cheap enough to call three thousand times. Where you would rather do it in one request, priceAirFiles takes a list and returns one result per file, in order, each with its own ok.

a batch, one result per file
import { priceAirFiles } from "./commission-sdk.js";

const files = [{ name: "26123556000.M07", text: await Deno.readTextFile(path) }, …];
const results = priceAirFiles(files, { config: contracts, subAgentId: SUB_AGENT });

results.filter((r) => !r.ok).forEach((r) => console.warn(r.file, r.error));

§4 — Reference

FieldMeaning
prefillThe value to write into a commission field, or null. See §5.
outcomeCALCULATED · NIL · NO_RULE · AMBIGUOUS · INCOMPLETE · NO_CONTRACT · ERROR
carrierCommissionWhat the consolidator earns from the carrier.
subAgentCommissionWhat is left after the retention. Null when priced as the consolidator.
claimed / claimedAsWhat the document's own FM element records. "percent" means it was a rate — FM*M*8 is eight per cent, not eight dollars.
clauseWhich condition decided it, in words. Put this next to the number in your UI.
warningsWhat the reader could not resolve. Never fatal, always reported.

Every amount is a decimal string

Not a number. "104.72", never 104.72. A float cannot hold every cent exactly and a bigint does not survive JSON.stringify, so money crosses this boundary as text and your database column stays a decimal. The whole response round-trips through JSON unchanged — a test pins it.

§5 — The rule that matters

When to trust the number

A figure your CRM must not use looks exactly like one it should. So the decision is made in the SDK, not left to whoever writes the integration.

the only branch your integration needs
if (doc.prefill !== null) writeCommissionField(doc.prefill);
else                     sendForReview(doc.explanation);

prefill carries a value only when the outcome is CALCULATED or NIL — the contract answered, and the answer is either an amount or an explicit nothing. Every other outcome yields null:

OutcomeprefillWhat it means
CALCULATEDan amountA clause matched and produced a figure.
NIL"0.00"A clause matched and says nothing is due — a positive assertion, not an absence.
NO_RULEnullNo clause covers this document. Not the same as nil, and not safe to treat as zero.
AMBIGUOUSnullTwo clauses match equally. Only the contract's owner can say which was meant.
INCOMPLETEnullThe document is missing something a clause needs — a reissue with no record of what it replaces, an airport not in the geography table.
NO_CONTRACTnullNo contract is configured for this IATA number.
The distinction that costs money

NIL and NO_RULE both come to nothing, and treating them alike is how a system quietly loses commission. Nil means the contract was read and pays nothing here. No-rule means nobody has told the software about this business yet — and every ticket like it is unclaimed until someone does.

the same ticket, missing its tour code
{
  "carrierCommission": "0.00",
  "prefill":  "0.00",
  "outcome":  "NIL",
  "ruleId":   "ly-2026-NO-TOUR-CODE",
  "clause":   "tour code 0NYZE71545 required",
  "explanation": "no commission is due (tour code 0NYZE71545 required)"
}

Zero is the right figure and it is safe to write. The clause is what makes it actionable: this ticket earns nothing because a tour code is absent, and the same message across a week's feed is a ticketing problem worth fixing at the source.

§6 — Reference

checkStatement(csv, files, options)

Takes the consolidator's statement and the documents it should cover, and returns the rows where they disagree. Any delimited export works: the reader finds the header under a letterhead, maps columns by their headings, reads accounting notation, and drops a totals row rather than reading it as a ticket.

reasonMeaning

Why fees are separate

Without a fee schedule there is no way to know whether a deduction is contractual. Folding it into one variance would hide which half is in question — so a line paid exactly right with money withheld reads as DEDUCTION, not as a shortfall. You would otherwise see "35.00 short" and not know whether you were underpaid or correctly charged.

§7 — Configuration

The contract file

Plain JSON. Keep it beside the function, in a database column, or in your CRM's settings — the SDK only reads what you hand it. seedConfig() returns the EL AL letter already entered, which is the fastest way to see the shape.

contracts.json
{
  "version": 1,
  "consolidators": [{
    "id": "mst",
    "name": "Main St Travel",
    "iata": "33535983",          // how a ticket finds this contract
    "retainsPoints": "1.00",     // of the fare; the sub-agent takes the rest
    "contracts": [{
      "id": "ly-2026",
      "carrier": "LY",
      "title": "EL AL Agency Commission Letter 2026",
      "issuedFrom": "2026-01-15",
      "issuedTo": "2026-12-31",

                  "K":"7.00","V":"7.00","S":"7.00","L":"7.00","H":"7.00","N":"7.00",
                  "C":"6.00","J":"6.00","Q":"6.00","B":"6.00","P":"6.00",
                  "W":"5.00","Y":"5.00","M":"5.00",
                  "G":"3.00","O":"3.00","U":"3.00" },
      "includeYq": false,                  // does YQ count toward the fare
      "requiredTourCode": "0NYZE71545",    // absent forfeits the commission
      "originIn": ["US","CA"],             // travel must originate here

Add a consolidator by adding an object with its own iata; add a carrier by adding a contract. A batch containing both sorts itself, because each ticket names the IATA number it was issued under. The same JSON is what the standalone app reads and writes, so a configuration built by clicking in the app can be exported and deployed.

§8 — Alternative

If your CRM is not JavaScript

A small HTTP server ships with the SDK. No framework, no database, no session — it holds the configuration in memory and answers questions about text it is handed.

run it beside your CRM
node --import tsx packages/sdk/src/server.ts --config ./contracts.json

# POST the file itself
curl -X POST localhost:8787/price --data-binary @26123556000.M07

# check a statement against a batch
curl -X POST localhost:8787/statement -H "content-type: application/json" \
  -d '{"statementCsv":"...","files":[{"name":"a.air","text":"..."}]}'

curl localhost:8787/health
Before you expose it

It binds to 127.0.0.1 deliberately. It answers questions about commercial contracts and passenger names, so putting it on a public interface is a decision to make on purpose, with authentication in front of it.

§9 — Honesty

What is proven, and what is still assumed

You asked to be able to trust this completely. The arithmetic you can. Parts of the contract reading are still a careful reading of a document that does not say.

Proven

  • The arithmetic. 267 tests. Exactness at every scale, rounding modes, splits that sum back to the whole, a batch of four thousand documents reconciling to the cent.
  • The parser, against five real AIR records from your own feed — a straight issue, two exchanges, a three-passenger booking and a published-fare reissue. Every trap those files exposed has a regression test: multi-passenger records, waitlisted segments that look like coupons, three dates in one element, FM as a rate rather than an amount, EUR pricing, documents with no coupons at all.
  • The contract reading, mechanically. A contract entered through the app prices identically to one written by hand — the same 180.00 on a D-class fare, the same forfeiture with no tour code, the same nil ex-Israel.

Assumed

  • The commissionable fare. The EL AL letter never states whether commission is on base fare or base plus YQ. Base only is assumed. On a fare with a 386.00 YQ at 9% that is 34.74 a ticket — the largest single number in the system. No EL AL sample carries YQ at all, since the surcharge is filed inside the fare as Q, so it may not arise on this carrier.
  • How a half round trip splits the fare. Clause 12.1 prices per direction but does not say how to divide the fare between them. An even split is assumed; a fare-calculation split disagrees on any open jaw.
  • Reissues and refunds. The letter is silent. Netting against what the replaced ticket earned is assumed, which is the reading the Amadeus FO element is built to support.
  • Whether clause 14 is enforced. Not one of your sample tickets carries the required tour code. If EL AL enforces it, that is real money forfeited every week; if not, the software is understating. One statement from your consolidator settles it.
How the software behaves about this

Every assumption above is a field in the configuration, not a decision buried in code. includeYq is a boolean; the tour code is a text box; the scope is a dropdown. When you learn the answer, you change the setting and every figure moves — no rebuild, no developer.
